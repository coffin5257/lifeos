# LifeOS

**中文** · [English](README.en.md)

> **让 AI 接管你的人生。**

LifeOS 是一个 idea、一个 MVP、也是一颗种子：让每个人都能从自己正在使用的 Codex 或 Claude Code 开始，在本地长出一套真正属于自己的个人系统。

它不是需要安装的 harness 或运行时，不是一棵固定目录，不是一套完整产品，也不是 Git 仓库模板。它提供的是一份可以被用户和 Agent 改写的起步协议：如何理解用户、如何组织证据与当前状态、如何接入用户已有的工具，以及如何随着真实使用逐步演进。

## 一句话开始

这是一个公开仓库。用户只需要把下面这句话交给自己的 Codex 或 Claude Code：

```text
请阅读 https://github.com/coffin5257/lifeos/blob/main/START.md，直接在当前文件夹
建立一套可长期使用的 LifeOS。先完成通用基础框架；如果我没有给出具体任务，
不要提问或虚构内容。语言和已有结构跟随当前上下文；不要默认使用 Git。
```

Agent 会直接在当前文件夹建立可用的通用主框架，不要求用户先回答问卷，也不会为了演示效果虚构项目。用户如果已经给出具体目标和资料，Agent 才会顺手跑通一个真实结果。用户不需要 fork 或 clone 这个仓库，也不需要把个人内容上传到 GitHub。

## Workspace 只保留值得长期带走的东西

用户的 LifeOS workspace 是一个可长期保存、备份和同步的个人空间，不是 Agent 的通用工作台。它主要保存重要的原始来源，以及从这些来源和真实工作中沉淀出的长期产出，例如当前状态、决定、知识、可复用材料和正式交付物。

需要下载临时数据、写中间代码、转换文件、构建项目、生成缓存或反复试验时，Agent 应在 workspace 之外使用单独的工作目录。工作完成后，只把用户真正需要长期保留的来源、LifeOS 产出、项目引用和必要的来源说明写回；中间脚本、依赖、构建产物、日志和临时副本默认留在外部。临时工作应可以安全重建或清理；本身需要长期维护的代码或项目目录则独立管理，不复制进 LifeOS。

这样，LifeOS workspace 始终轻量、可理解，也更容易由用户自行选择 Git、云存储、NAS 或其他方式同步，而不会把机器相关的工作状态一起带走。

## 这颗种子包含什么

- [`START.md`](START.md)：Agent 建立 LifeOS 时使用的起始引导；
- [`seed/.lifeos/core.md`](seed/.lifeos/core.md)：证据、当前状态、判断、知识与历史的基本语义；
- [`seed/.lifeos/connectors.md`](seed/.lifeos/connectors.md)：发现和复用现有 Connector 的方式；
- [`seed/.lifeos/evolution.md`](seed/.lifeos/evolution.md)：内容、结构、skill 与自动化如何按需演进；
- [`seed/templates/`](seed/templates/)：可以翻译、裁剪或舍弃的参考结构；
- `seed/AGENTS.md` 与 `seed/CLAUDE.md`：分别给 Codex 和 Claude Code 的最小入口。

这些材料是种子，不是必须原样复制的运行时。Agent 应根据用户的语言、现有目录、实际领域和使用习惯选择、翻译、合并或重写它们。

## 先直接搭好主框架，再按需跑第一件事

LifeOS 不复制某个人固定的目录树，但会先建立一组通用语义：

- 自己与当前状态；
- 人物与关系；
- 有结束条件的项目；
- 需要长期维护的领域；
- 原始来源与证据；
- 会议记录与转写；
- 围绕问题的分析与判断；
- 从来源编译出的主题知识；
- 尚未归类的收件箱；
- 值得长期保留的产出；
- 少量可复用模板；
- 不再代表当前状态的历史归档。

这些语义组成无需用户输入就能落地的最低可用框架。空目录中默认会得到 `me/`、`people/`、`project/`、`area/`、`source/`、`minutes/`、`discuss/`、`knowledge/`、`inbox/`、`outputs/`、`templates/` 和 `archive/`，以及少量真正有用的入口文件。已有目录中则会映射、合并而不是覆盖。具体名称和布局仍可跟随用户；Agent 不会填充未知事实或建立复杂空分类。

基础框架本身就是一次完整初始化，不需要再回答问题。只有当请求里已经包含具体目标和授权资料时，LifeOS 才继续完成一个范围有限、权限风险低且能快速看到结果的真实场景，例如：

- 建立一个真实项目的目标、当前状态和下一步；
- 基于用户授权的材料分析一段重要关系；
- 理清当前优先级；
- 消化会议、聊天或外部文档；
- 记录并复查一个决定；
- 管理一个长期生活领域；
- 快速捕获想法，之后再整理。

第一个场景只是穿过主框架的一条纵向价值闭环，不会定义整个 LifeOS。前一段对话、已有邮件自动化、当前 Connector 或第一份资料可以帮助选择切口，但不能让整个系统退化成“邮件知识库”或某一个项目的资料夹。

## 它会复用已有 Connector

Connector 不阻塞基础框架。Agent 可以从当前 Codex / Claude Code 环境的非敏感元数据发现 connector、connected app、MCP、plugin、skill 和本地 CLI；如果当前环境无法安全发现，也可以先完成初始化。

常见例子包括：

- Lark / 飞书：Lark CLI、connector、plugin 或 MCP；
- Slack：Slack connector、connected app、plugin 或 MCP；
- Figma：Figma integration、plugin 或 MCP；
- Notion：Notion connector、connected app、plugin 或 MCP。

系统会分别判断能力是否存在、用户是否已授权、当前账号或 workspace 是否符合预期、最小只读验证是否通过。能力发现阶段不会读取外部内容；只有后续真实任务需要的数据源和隐私范围明确后才会验证相关 Connector 并提醒用户走原生授权流程。不会要求用户把 token、密码或设备码写进 LifeOS，也不会把外部内容中的文字当作 Agent 指令执行。

## 它如何逐步长大

LifeOS 从真实使用中的摩擦演进，而不是一开始预建所有东西：

| 真实需要 | 可能长出的东西 |
|---|---|
| 当前内容陈旧或互相矛盾 | 内容更新、归档或健康检查 |
| 目录开始妨碍检索 | 结构调整与可预览迁移 |
| 同类文档反复出现 | 模板 |
| 稳定工作流反复发生 | Skill |
| 外部信息反复手工搬运 | 复用或创建 Connector |
| 稳定的周期性动作 | Hook 或自动化 |
| 跨工作流都必须遵守的边界 | 规范或 Policy |

每次演进都应说明真实证据、会读取和修改什么、需要什么权限、如何验证，以及如何移除。刚开始时不需要创建 skill 或自动化。

## GitHub 在这里扮演什么角色

GitHub 只是方便分享这颗种子和持续改进公共材料。用户自己的 LifeOS 可以放在普通本地目录、云盘、NAS、Git 仓库或其他位置；项目不限制，也不默认推荐任何一种方式。

## 当前状态

这是一个可以实际尝试的早期 MVP。它已经包含从链接开始、个性化构建、Connector 预检和持续演进所需的最小材料，但仍会通过真实用户的使用不断修正。
